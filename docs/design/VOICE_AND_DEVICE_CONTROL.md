## Voice architecture

**Product requirements:** a suitable local wake word, inexpensive/local commands, high-quality personalized speech interaction, interruption, provider choice, offline fallbacks and urgent JARVIS app calls. S1-M0183 and S2-M0033/M0035/M0037 establish this direction. No exclusive speech vendor is selected. [R042–R044]

The voice path is: activation → audio session → speech recognition → deterministic intent check → authorized retrieval/model/tool work → speech synthesis → outcome. Audio transport, ASR, conversational model and TTS are replaceable adapters. A real-time provider may combine several stages, but it still uses the same policy, context and cost boundaries. A proprietary cloud model is not a downloadable phone model.

| Tier                          | Examples                                                                               | Offline contract                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Deterministic local command   | Open an app, stop speaking, inspect a cached timer, pause collection                   | Works without a model when the relevant OS action is supported                     |
| Local speech / selected model | Transcribe a short instruction, classify intent, extract a date, summarize cached text | Works only with installed assets and adequate device resources; ambiguity can wait |
| Cloud conversation            | Complex planning, richer natural dialogue, difficult retrieval reasoning               | Requires network, allowed context and cost reservation                             |
| Premium escalation            | Complex decisions or high-value Council work                                           | Explicit routing justification within hard caps; never a hidden fallback           |

The owner wants speech recognition that handles his normal phrasing and personal names. Use opt-in vocabulary/context hints and evaluate real utterances, noise, accents and Bluetooth paths. Do not assume that fine-tuning or storing all audio is necessary. Raw wake-word audio should remain local in a bounded buffer by default; upload only the permitted activated interaction. Exact audio retention is part of Q02.

Barge-in should stop current speech promptly, mark any interrupted response and preserve completed action outcomes. Cancellation of speaking is different from cancellation of an already-started external action. Reconfirm only if the interrupted instruction makes the action ambiguous. Prevent microphone/TTS feedback loops and distinguish user speech from JARVIS playback. Show when the microphone is active.

Default assistant selection, private APK installation and Device Owner status remain distinct capabilities.

## Incoming JARVIS call

**Product requirement:** JARVIS can present an urgent interaction like an incoming app call, with answer/decline and a live voice session. S2-M0037 explicitly distinguishes this from requiring a virtual telephone number. It may be used when an important delegated conversation, deadline or repeated ignored alert deserves escalation. It must identify itself as JARVIS, not imitate a carrier call or another person.

Android Core-Telecom supports app calling integration and call/audio lifecycle; its guidance requires prompt call notification after adding a call. Full-screen intent eligibility and user permission are separately constrained, particularly for apps targeting Android 14+. **Confirmed platform mechanisms; JARVIS presentation needs prototype and device testing.** [Core-Telecom](https://developer.android.com/develop/connectivity/telecom/voip-app/telecom), [full-screen intent restrictions](https://developer.android.com/about/versions/14/behavior-changes-14#secure-fsi)

Prototype states: escalation created → delivery attempted → ringing/notification shown → answered/declined/missed → voice connected/failed → resolved or queued follow-up. Record which stage was actually observed. A push being accepted does not prove the phone rang. Answering activates the appropriate microphone/audio session; no ambient listening before answer is implied.

If full-screen presentation is unavailable, use an allowed high-priority JARVIS notification with answer/open controls. Respect DND, lock-screen privacy and the owner's escalation rules; do not promise bypass. Suppress duplicates across channels and stop retrying after acknowledgement or configured limits. If offline, a locally scheduled supported alert may work, but a new server-originated call cannot reach a disconnected phone. Fall back to a retained important alert when connectivity returns, with freshness checks.

## Device actions and automation ladder

Prefer a direct Android intent or supported provider API. Then use an exposed notification action if it actually supports the intended operation. Use Accessibility only for a bounded visible UI workflow with recognized app/version, preconditions and postcondition checks. Escalate to the owner when secure unlock, unsupported controls or ambiguity intervene.

For each action, record target package/account, expected current state, permitted input, completion evidence, timeout and recovery. Stop if the wrong screen appears. Do not keep tapping coordinates through an unknown layout or declare success because an action was dispatched. Financial and destructive actions retain their stricter authority checks even when implemented through UI.

The Love8 question is a test of stale third-party state: check integration, refresh semantics and permission health first, then a supported app refresh if useful. “Open it while locked” is not a guaranteed feature and should not become a recurring unlock workaround. [R041]

## Device Owner and Knox escalation

Start with ordinary permissions on stock Android. Device Owner is optional when a concrete requirement such as stronger distraction control cannot be met adequately otherwise. Provisioning may require a fresh device or enrollment flow; no reset is part of this reconstruction. Test that normal phone use and emergency access remain intact.

Knox enrollment deserves its own proof: Samsung documents that ADB Device Owner provisioning can skip prerequisites needed for Knox license activation. Use supported provisioning guidance for the selected feature rather than assuming an ADB command is equivalent. [Knox provisioning caveat](https://docs.samsungknox.com/dev/knox-sdk/kbas/using-adb-to-provision-a-fully-managed-do-device-causes-unexpected-behavior-during-the-knox-license-activation-process/)

Root/ROM is not the next automatic step after one failed experiment. First establish a repeatable stock limitation, product importance, supported alternatives, compatibility cost and recovery path. See [ARCHIVE_OLD_DIRECTIONS.md](../archive/r1-product/ARCHIVE_OLD_DIRECTIONS.md).

## Device test matrix

Test the selected S26 Ultra RAM/firmware/carrier variant with real daily-use load: unlocked and locked; screen off; battery saver/Doze; charging/thermal load; Bluetooth headphones/car; incoming cellular call; competing microphone use; network loss; app kill/reboot; permission revocation; DND; secure screens. Measure wake accuracy, false wakes, latency, battery drain, local-model memory pressure and recovery.

Use push-to-talk and a visible local command surface as dependable fallbacks while wake-word behavior is being validated. Keep voice vendors and model sizes configurable until the tests establish a useful combination. A strong chipset and more RAM improve available resources; they do not remove Android permission or background-execution rules.
