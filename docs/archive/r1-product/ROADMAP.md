# Roadmap

Responsibility: build order based on dependency and usefulness. These are new product phases, not the historical Phase 0–3.6/C4/C7 labels in old engineering reports. Timing is intentionally not invented.

The product should become useful before it becomes visually impressive. The owner explicitly questioned whether there was a real brain behind infrastructure in S1-M0181. Preserve existing tested foundations while proving user value. [R003, R019, R059, R081–R084]

## Before new implementation

Inspect the actual repository and current deployment against [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). Determine whether the reported final cloud matrix remains incomplete and whether Convex is still paused. Do not rerun migrations already reported applied merely because an older assistant said to do so. Read actual migration/state evidence and make the next engineering step concrete.

Verify existing job/action/policy invariants and identify reusable code. Resolve numeric API caps before paid calls. Use supplied/synthetic data and drafts while sensitive collection and live sending settings are unset. No requirement to finish every future owner preference before useful development begins.

If the reported C7 configuration blocker is still present, resolve the narrow authorization/path in Q06 after inspecting current state. This is separate from selecting a new hosting architecture and does not require rerunning the successful migration.

## MVP — trustworthy personal core and thin Android access

Build reviewed onboarding, owner authentication, inspectable facts/preferences, a small but durable exact-searchable corpus, commitments/conditional intentions, useful briefings, drafts, Cases in minimal form, action status, cost admission and scoped retrieval. Connect one dependable communication path and a thin Android client. Establish a basic real HOME surface with local app launching as part of early Android validation; the complete three-page integration is not a visual prerequisite for testing the core.

Reuse the existing model gateway and durable execution where verified. Start with deterministic commands and one suitable cloud adapter under configured caps; benchmark a selected local model in parallel with the phone foundation before making broad offline promises. Multiple-provider architecture should not require integrating every provider in the first release.

**Exit:** the owner can supply context, ask a source-backed question, create a commitment, receive a useful follow-up, inspect/correct memory and understand an action's actual status. Offline Home remains usable. Cost and authority tests pass. At least one real end-to-end useful workflow is demonstrated; HTTP health alone does not pass.

## Phase 2 — daily Android and unified personal context

Complete the left/center/right Home behaviors. Prototype Beeper Desktop hosting, account/network support, historical coverage and live reconciliation; then deliver unified read/search/draft and supported owner-driven sends. Add selected Notification Listener capture, deliberate screenshot imports, calendar/email reads and event extraction. Add conservative background location only after explicit collection settings and device measurements.

Deliver push-to-talk, deterministic local commands, selected offline speech/model tasks and replaceable conversational voice. Prototype wake word, urgent JARVIS call presentation, Accessibility actions and OEM recovery under real daily conditions. They need not block useful typed/search/draft behavior.

**Exit:** current chats and saved context reliably appear, coverage/freshness are visible, personal retrieval is useful, source corrections propagate, and background features meet measured phone reliability. No secure unlock or presence guarantees are assumed.

## Phase 3 — bounded delegation and text Council

Enable timed Handoff/Sleep Handoff only after Q03, grants and connector/device tests. Add escalation, owner takeover, morning briefing and partner/context calendar extraction. Expand persistent Cases and scoped operational email/browser work where a specific useful task and authority exist.

Build Council Chat with distinct prompts/objectives/context/tools/private memory, bounded asynchronous triggers, chairman synthesis, evidence and actions. Start with a small useful roster; prove finance/operator disagreement and denied cross-domain access. Add providers only when they improve the workload.

**Exit:** a delegated period ends cleanly with accurate context and no duplicate/unauthorized sends. A Council decision produces tracked follow-through. Parent/child budgets and revocation work across concurrent agents.

## Advanced product work

Add richer Reality Debugging, grouped recovery/undo, repeated-work learning, isolated desktop/cloud execution and complex multi-day Cases. Develop Boardroom voice, rendered characters, shared evidence, optional camera and interruption over the proven Council core. Visual assets and character polish must not create a second history or authority system.

Future approved personal tools include the owner's **Iron & Intervals** training project, food/nutrition, gym/workout/running and calendar apps that write directly to JARVIS; journal retrospectives joining photos/music/places/activity; Letterboxd-inspired movie watched-date/rating/review history; and a calculator that can preserve meaningful calculation context or ask what a calculation relates to. These are remembered user ideas, not a mandate to replace all apps before JARVIS is useful. [S1-M0003/M0187/M0189; R013–R015]

Read-only finance intelligence can expand to a scoped payment/purchase broker when provider eligibility, owner authority and reconciliation are established. The proposal is integration with appropriate payment services, not a custom card network or automatic financial punishment. Music-history and wearable integrations remain evidence-driven: Apple Music is the known service, Spotify a conditional option; WHOOP/Oura and other health sources are not selected purchases.

S8-M0003 also floats a JARVIS Mail client using the owner's existing domain. Preserve it as a future possibility: JARVIS can own the interface and intelligence while an established provider supplies mailbox transport, spam handling and delivery. Domain/MX ownership is not a requirement to run a mail server. This idea is separate from the already desired email triage and future task-scoped sending capability. [R094]

**Exit:** each added capability resolves a real recurring burden, has reliable evidence/authority/recovery and fits observed cost/resource limits. It does not enter production solely because a demonstration looks convincing.

## Scope-control rule

Do not build all integrations, all agents or all device privileges at once. For each increment, name its user outcome, dependency, evidence source, permission/cost envelope and exit test. If a workaround exists only because JARVIS lacks a direct integration, compare fixing the underlying data/control path before automating repetitive taps. If a deployment migration does not improve a demonstrated constraint, it need not precede user value.
