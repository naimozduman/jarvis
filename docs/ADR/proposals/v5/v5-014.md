# Trusted time and restore-safe execution

Status: proposed. Owner acceptance: none. Repository ADR number: unassigned. Predecessor proposal: none.

## Context

The owner requested an engineering system for taking over the existing JARVIS codebase, retaining the complete product direction and using the review findings without another speculative redesign.

## Decision

Use fresh trusted time after lock acquisition and separate restore/kill epochs. Quarantine restored external effects for reconciliation.

## Alternatives considered

Reject client-clock authority and automatic replay of restored approvals/outboxes.

## Security and privacy impact

Limits replay risk but still requires actual database, provider and incident drills.

## Consequences

New tooling remains a candidate until trusted installation. Local tests establish tool behavior, not deployment, key custody or application correctness. Budget and authority decisions remain unapproved.

## Migration

Use the V5 mission transition and reconciliation maps. Preserve accepted ADRs, applied migrations, active schemas and dirty work. The operator assigns an unused ADR number only at acceptance. No acceptance is inferred from this file's presence.

## Verification and rollback

Run targeted pack tests and actual integration tests before activation. Revert candidate tooling through a reviewed patch, but never roll back external trust/restore epochs or replay dispatched effects. Record exact acceptance/rejection evidence.
