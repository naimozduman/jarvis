# J5-M21: Build the browser and research surface

## Outcome

Build a read/organize browser surface and research-domain integration over the same Core. Preserve tabs/spaces/source references and cross-surface project continuity. Review platform feasibility for Windows, macOS, Android and iOS independently. Effectful browser capabilities additionally require completed executor admission.

## Read and resolve context

Use the canonical `AGENTS.md` entry first. Then generate the `browser` context packet for `J5-M21` with `tools/jarvis-v5/context.py`. Read the exact source files in that packet when a change depends on implementation details. The PRD is long-form reference; do not load every section for an unrelated task.

Required subsystem documents: `docs/architecture/BROWSER_ARCHITECTURE.md`, `docs/security/PRIVACY_TIERS.md`, `docs/integrations/FIRST_PARTY_SDK.md`.

## Admission and prerequisites

Dependencies: J5-M13, J5-M07. A roadmap flag is not completion evidence. `mission_gate.mjs` checks trusted receipts before an implementation run. M00 audit and M01 owner-controlled bootstrap preparation remain explicit exceptions; neither grants runtime or deployment power. If a prerequisite is missing, produce a bounded blocker report, not an edited completed flag.

## Work method

1. Confirm source checkpoint, dirty-state preservation and input hashes. Recheck a source observation if the current file differs.
2. Record the smallest keep, repair, migrate, replace or retire decision. Preserve valid current interfaces and tests. A replacement requires a written incompatibility reason.
3. Name affected requirements, invariant IDs, schemas, producers, consumers and mapped evaluations in a change-impact record before edits.
4. Implement one end-to-end slice in the isolated builder workspace. Use synthetic fixtures, bounded execution and scrubbed credentials. Stage tools or database work are separate owner-authorized operations.
5. Run existing relevant suites as discovered in the actual repository, plus the targeted proof below. Record exact commands, exits, counts, source/artifact hashes and tests not run. Never repair a failure by weakening its judge.
6. Submit the exact candidate for independent verification. The builder records `ready_for_verification`; trusted completion is a separate signed receipt.

## Required proof

Research continuity, private-context exclusion, malicious page instructions, stale snapshots and unauthorized uploads are tested. A provider login is never a tool permission.

Also exercise the relevant negative boundary: malformed input, foreign owner, duplicate request, stale revision, revocation, missing configuration, timeout and unavailable dependency. An inapplicable case needs an explicit reason, not an invented passing test.

## Non-goals and stop conditions

No custom browser engine requirement for the first useful surface and no automatic browser-submit rights.

Stop for unknown accepted history, unapproved cost or authority, unexplained source drift, or a failing critical invariant. Do not silently downgrade a provider, privacy class, test requirement or authentication step.

## Migration and rollback

Use expand/contract for active data and protocol changes. Name the active reader and writer version and the point after which rollback requires forward repair. Reverting code is not permission to reverse a real-world effect. Keep outbox operation identity and reconciliation records across rollback. For tooling-only work, preserve the original pack and generate a per-file integration plan.

## Handoff

Update the one descriptive engineering state, `governance/STATE.json`, only after adoption of the V5 handoff convention. Before adoption, write the same shaped report to the approved scratch location. Include branch/head, dirty files, changed artifacts, commands, failed checks, pending owner decisions and next safe step. Important milestones receive append-only progress evidence. Do not start another mission automatically.
